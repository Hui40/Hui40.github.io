什么是Skills？给AI写一本员工手册

Hui2026-11-222026-11-23

开头

你有没有让 AI 帮你整理过会议纪要？

我有过。

第一次，我交代得很细：按项目分组，每条待办标出负责人，最后单独列一个本周完成清单。

它做得挺好。格式清楚，一条不落。

第二天，我开了个新对话，只说了一句：“再帮我整理一份。”

它又还我一大段流水账。

我只好把昨天那串要求，从头再打一遍。

你看，问题不在它笨。

它只是不记得，你们这儿的规矩。

我把这件事做成了视频，也在视频里讲了 Skills 是什么。文章会比视频慢一点，把里面的细节拆开讲。

看完这篇，你会明白三件事：

  • Skill 到底是个什么东西——它不是模型，也不是插件
  • 它为什么能解决“每次都要重复解释”这个老毛病
  • 怎么给 AI 写第一本员工手册，今天就动手

知识科普

一、它不是笨，它是每次都从零开始

先说一个很多人误会的地方。

AI 在同一个对话里，是能记住前面说过的话的。你十分钟前让它“按项目分组”，它后面还会照做。

但只要你点一下“新对话”，它就像换了个人。

这不是它故意装傻。大多数聊天工具里，新对话不会自动继承旧对话的内容——上一段对话的上下文，到这儿就断了。

有些产品做了“记忆”功能，能记住你的名字、偏好、说话习惯。但那是另一套机制，不等于它记住了你们公司的周报模板、文件命名规则、客户邮件的语气。

你可以做个小实验。

在同一个对话里，先告诉它“以后写邮件都用敬语”，再让它写一封。它照做。

然后开个新对话，同样让它写一封。它多半会回到自己的默认风格。

所以，想让 AI 稳定地按你们的方式干活，你只有两条路：

要么每次重新解释一遍，要么把规矩写下来，放在它伸手就能拿到的地方。

第一条路你已经走过了，很累。第二条路，就是这篇要讲的 Skill。

二、Skill 是什么：一本写给 AI 的员工手册

你可以把 AI 想成一个刚入职的同事。

脑子很好使，写代码、做表格、读长文档，样样都行。

但你们公司的规矩，它一条都不知道。

周报怎么写，文件怎么命名，给客户发邮件用什么语气，哪些话不能说——你不说，它就按自己的习惯来。

想把一个新人带出来，最省力的办法不是每天口头交代，而是给他一本员工手册。

Skill，就是这样一本手册。

它不是新模型，也不会让 AI 突然变聪明。它就是一个文件夹，里面放一页说明书，告诉 AI：这件事该怎么做。

1. 一个文件夹，一页说明书

一个 Skill 的最小结构，就这么点东西：

最外面是一个文件夹，名字随你起，比如 weekly-report。

里面必须有一个 SKILL.md。这就是那页说明书。

旁边还可以放模板、参考资料、能直接运行的小脚本。

2. 开头两行：我叫什么，什么时候该用我

SKILL.md 的开头，是一小段用三条横线包起来的信息：

这两行里，description 是最重要的。

AI 平时看不到正文，它先看到的就是这一句简介。

这句话写得清不清楚，直接决定 AI 会不会在需要的时候，把这本手册翻出来。

你可以把它理解成书脊上的字。

书架上有二十本书，你不可能把每本都抽出来翻一遍。你先看的是书脊：这本书叫什么，大概是讲什么的。

description 就是书脊。

写的时候记住一个原则：把你希望它被触发的场景写进去。

不要写“一个很有用的助手”，要写“用户要写周报时使用”。

前者等于没说，后者 AI 一看就知道什么时候该拿。

反面例子和正面例子放一起，你感受一下：

不推荐的那句，放在任何一本手册上都成立，等于什么都没说。

推荐的那句，把“什么时候用”和“用来干什么”都写进去了，还顺手带了几个用户可能会说的词。

name 一般用小写字母和短横线，别用空格，也别写中文。文件夹名和它保持一致，最省事。

3. 正文：把话说到能照着做

三条横线下面，就是正文。

正文不用写得文采飞扬，它更像一张操作单：

就这么简单。

判断写得好不好，有个很土的标准：把这段交给一个刚来的实习生，他能不能照着做完。

如果他看完还得跑来问你“数据在哪”“模板长什么样”，说明你还没写清楚。

4. 旁边还能放模板、资料和脚本

一个 Skill 不是只能放一页说明，它还能带三样东西：

放什么 干什么用 例子
模板 固定输出格式 周报模板、邮件模板、PPT 大纲
资料 提供背景知识 品牌语气说明、产品参数、常见问答
脚本 干确定性的活 核对数字、转换格式、生成图表

脚本这一样，很多人会忽略。

有些事，让 AI 一步一步算，又慢又容易错。写个小脚本，让它直接运行，结果反而稳。

比如“核对这周的数字有没有对不上”，与其让 AI 盯着两张表一行行看，不如写个脚本跑一遍。

能交给代码的，就别让 AI 硬猜。

别把密码、密钥、客户隐私写进 Skill。

Skill 是放在项目里、可以随项目共享的文件。你在里面写的每一个字，读到它的人——包括 AI——都能看到。

API key、数据库密码、客户的真实姓名和电话，都不该出现在这里。示例数据用假值，比如 api.example.com、张三、13800000000。

三、AI 是怎么用它的：渐进式加载

讲到这儿，你可能会问：

“如果我装了二十本手册，AI 是不是每次都要把二十本全读一遍？”

不会。

它要是真这么干，上下文早就撑爆了，你也得为这些字数付钱。

真实的做法，更像你在书架前找书：

第一步，只看书脊。

每本手册的名字和一句简介，会一直摆在 AI 面前。这部分很短，几十个 token 的量级，装二十本也不算什么。

第二步，翻开正文。

当你提到“周报”，它判断这件事和周报那本有关，才把 SKILL.md 的正文读进来。

第三步，需要什么再拿什么。

正文里写着“套用 templates/weekly.md”，它才去读模板；写着“运行 scripts/check.py”，它才去跑脚本。

这套办法有个名字，叫渐进式披露（Progressive Disclosure）。

我在视频里把它叫“渐进式加载”，因为对小白来说，“加载”比“披露”好懂。你知道是这么个意思就行。

层级 内容 什么时候加载 大概占多少
第一层 名字 + 一句简介 一开始就在 几十个 token
第二层 SKILL.md 正文 判断相关时 通常几千 token 以内
第三层 模板、资料、脚本 真正用到时 按需，不提前占地方

这也是为什么，写 Skill 的时候要克制。

正文不是越长越好。你把所有细节都塞进正文，等于让 AI 每次都背一遍整本手册，又慢又贵。

该展开的细节，放附件里。正文只留主干。

四、用起来是什么感觉

说了半天结构，你可能还是没感觉。

我们走一遍。

你打开 AI，说一句：

按老规矩，把这周的周报写了。

没有解释格式，没有说数据在哪，也没有提模板。

AI 看到你的请求，发现装过一个叫“周报”的 Skill，简介里写着“用户要写周报时使用”。

它把正文翻开，照着做：

  1. 去共享盘读本周数据
  2. 套用品牌模板
  3. 跑一遍检查脚本，核对十二项数字
  4. 按项目分组，标出待办和负责人

最后交给你的，是一份格式稳定、语气一致的周报。

没有 Skill 有 Skill
你每次要做的 把要求重新打一遍 说一句“按老规矩”
输出格式 看它当天心情 每次都一样
数据从哪来 你得告诉它 手册里写着
出错概率 漏步骤、忘格式 步骤固定，还能跑脚本核对

注意，它不是变聪明了。

它只是终于知道了，你们这儿是怎么干活的。

如果它还是不用，先查三件事

第一，description 里有没有用户真正会说的词。

你写“用于生成周期性工作汇报”，用户说的是“帮我写周报”。这两个词对不上，AI 就可能判断不出来。

第二，这个 Skill 有没有装到当前环境里。

在电脑上装好的 Skill，不会自动跑到手机 App 里；项目里放的 Skill，换个项目就看不到了。先确认它在不在。

第三，这件事是不是真的该用它。

你让它“随便聊聊天”，它当然不会去翻周报手册。手册只在匹配的任务上才会被拿起来。

五、它不是什么，以及它和 MCP 的分工

有三个误会，先拆掉。

第一，它不是模型。

装一个 Skill，不会让 AI 的智商涨一点。模型还是那个模型，权重一个都没变。变的只是它手里多了一份说明书。

第二，它不是插件。

插件是给 AI 加新能力，比如让它能上网、能画图。Skill 不提供新能力，它提供的是“怎么把已有的能力用对”。

第三，它不是魔法。

如果 AI 根本碰不到你的数据库，写一百本手册也没用。手册教的是做法，不是权限。

顺便说一句，Skill 和“一段很长的提示词”也不是一回事：

一段提示词 一个 Skill
放在哪 聊天框里 文件夹里
能活多久 这一轮对话 装在哪，哪就能用
能不能带文件 不能 能带模板、资料、脚本
谁来维护 每次自己复制粘贴 改一次，后面都用
适合什么 一次性的小要求 反复出现的固定流程

提示词是“这次你听我说”，Skill 是“以后都按这个来”。

说到权限，就绕不开另一个东西：MCP。

如果你看过我讲 MCP 的那期，应该还记得：MCP 管的是“接”，让 AI 连上数据库、文件和外面的工具。

Skill 管的是“做”，告诉它活儿该怎么干。

MCP Skills
解决什么 AI 够不着外面的东西 AI 不知道怎么按你的规矩干
管什么 连接、工具、数据 流程、模板、规范
打个比方 给它手和眼睛 给它经验和规矩
没有它会怎样 只能聊天，干不了活 能干，但每次干得不一样

一个给它手和眼睛，一个给它经验和规矩。

工具决定它能碰到什么，手册决定它做得像不像你们的人。

这两样不冲突，很多时候是一起用的：MCP 把数据接进来，Skill 告诉它这份数据该怎么处理。

六、给 AI 写第一本手册

如果你已经有一件“每周都要重复交代”的事，那就可以动手了。

写一个自己的 Skill

第一步：挑一件事

别一上来就写“万能助手”。

挑一件你每周都要做、格式比较固定的事：周报、会议纪要、客户回访记录、竞品价格表。

越具体越好。

第二步：建文件夹

新建一个文件夹，名字用小写字母和短横线，比如 weekly-report。

在里面新建 SKILL.md。

如果你用的是 Claude Code，项目里的 Skill 放在 .claude/skills/ 下面；只给自己用的，放在用户目录的 ~/.claude/skills/ 下面。其他工具的位置不一样，看它的文档，思路是一样的。

第三步：写 description

这是最值钱的一行。

写清楚两件事：这件事是什么，什么时候该用它。

把用户可能会说的词也写进去，比如“周报”“本周总结”“汇报”。

第四步：写步骤

按你平时教新人的顺序写。

第一步读什么，第二步套什么模板，第三步检查什么。

能写成脚本的，单独放一个 scripts/ 文件夹，正文里写一句“运行它”。

第五步：试一次，再改

拿一个真实任务试。

看它卡在哪：是没找到 Skill，还是找到了但步骤看不懂，还是模板没套对。

卡在哪，就改哪一句。

改完再试一次。

展开看一份完整的 SKILL.md

写完你会发现，这件事本身不难。

难的是你愿不愿意花二十分钟，把脑子里那套“我们这儿都这么干”，第一次完整地写下来。

写完这一次，后面就省事了。

结语

好了，以上便是本期教学的所有内容了。

Skill 不神秘。它只是把你脑子里那句“我们这儿都这么干”，写下来，放在 AI 伸手就能拿到的地方。

想通这件事，这些现象就都对上了：

  • 新对话就忘——因为规矩从来没写下来，只留在上一段对话里
  • 每次都要重复解释——缺的不是表达能力，是一本手册
  • 同一个任务，格式时好时坏——缺模板，也缺检查步骤
  • 装了 Skill 但 AI 不用——多半是 description 写得太含糊，AI 判断不出什么时候该翻
  • 以为 Skill 能让 AI 变聪明——它只是流程，不是模型
  • 把 Skill 和 MCP 搞混——一个管“做”，一个管“接”
  • 手册越写越厚——正文要克制，细节放附件，用到再拿

最后送你一句话：

工具决定它能碰到什么，手册决定它做得像不像你们的人。
